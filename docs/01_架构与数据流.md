# 01 架构与数据流

> 这篇文章回答一个问题：**一句话从用户嘴里说出来，到机器人开口回答，中间到底发生了什么？**
> 每个环节在哪一秒、哪个线程、哪些数据在流动，全部说清楚。
> 面试时如果被问"讲讲你的架构"，你就按本文的顺序讲。

---

## 一、整体链路：五段式级联

```
   麦克风                VAD                  ASR                LLM                TTS              扬声器
 ┌─────────┐      ┌────────────┐      ┌───────────┐      ┌──────────┐      ┌──────────┐      ┌─────────┐
 │ 20ms 一块│─────▶│ 是不是人声? │─────▶│ 语音转文字 │─────▶│ 流式生成 │─────▶│ 文字转语音│─────▶│ 一块块播 │
 │  int16   │      │ 说完了吗?   │      │ "今天天气"  │      │ 逐 token │      │ 逐句合成  │      │ 可被打断 │
 └─────────┘      └────────────┘      └───────────┘      └──────────┘      └──────────┘      └─────────┘
       ▲                                                                                          │
       │                                     用户在这时候插话                                        │
       └──────────────────────────── 立刻停止播放 + 截断历史 ◀────────────────────────────────────┘
```

这就是**级联（cascade）架构**：把语音任务拆成"听、想、说"三个独立模型串起来。

> **面试点 1：为什么不用端到端 S2S（如 Moshi、Qwen2.5-Omni）？**
> 端到端延迟能压到 200ms 以内、打断更自然，但它**不可观测**——你没办法知道"这次慢是因为 ASR 还是因为 LLM"，
> 也没办法只换其中一环（比如客户要求换一个中文 ASR）。
> 级联架构每一环都是独立进程/独立模型，**可以单独替换、单独调优、单独测延迟**——
> 工程落地和排障友好得多。我们的目标是把级联的延迟压到接近端到端的水平（实测首字音频 283ms）。
> 这是"可维护性 vs 理论最优延迟"的取舍，不是技术落后。

## 二、三个线程：为什么必须多线程

这是理解整个程序的关键。**如果只有一条线程，你在播放语音的时候就没法听麦克风**，
那就永远不可能有"打断"。

| 线程 | 谁启动 | 干什么 | 阻塞在哪 |
|---|---|---|---|
| **主线程** | `main()` | 读麦克风 → 喂 VAD → 处理"开始/结束"事件；管理轮次 | `mic.blocks()` 每 20ms 吐一块 |
| **播放线程** | `BaseSpeaker.start()` | 从队列取音频块，一小片一小片写声卡 | `_q.get()` |
| **回答线程** | `_launch_respond()` | ASR → LLM → 切句 → 塞 TTS 音频进播放队列 | 网络/模型推理 |

```
主线程                       播放线程                  回答线程
  │                            │                         │
  ├─ mic.blocks() 拿 20ms 块    │                         │
  ├─ vad.process() ──start──▶  _begin_utterance()          │
  │                            │                         │
  ├─ vad.process() ──end────▶  _launch_respond() ────────▶├─ ASR
  │                            │                         ├─ history.add_user()
  │  (继续读麦克风!)            │                         ├─ LLM.stream()
  │                            │◀── speaker.enqueue() ───┤  逐句切分
  │                            ├─ 写声卡 (20ms 一片)      │  tts.synth()
  │                            │                         │
  ├─ vad.process() ──start──▶  _on_barge_in()            │
  │   (state==BOT_SPEAKING)    │                         │
  │      └─ stop.set() ────────┼────────────────────────▶│ 循环里检查到，退出
  │      └─ speaker.flush() ──▶├─ 停止，返回已播进度       │
  │         → 用进度截断历史    │  (last_flush_ms 实测)    │
```

**三个线程靠什么通信？**
- 主线程 → 回答线程：`threading.Event`（`self._stop`，一个"该停了吗"的开关）
- 回答线程 → 播放线程：`queue.Queue`（`speaker.enqueue()` 塞、`_q.get()` 取）
- 播放线程 → 主线程：回调函数（`on_start` / `on_end`），在播放线程里被调用

> **面试点 2：`self._stop` 这个 Event 为什么不能全局只有一个？**
> 我们踩过这个坑。原来在"开始一轮新说话"时就 `self._stop = threading.Event()` 重新创建，
> 结果：机器人正在回答第 2 轮，用户插话，代码创建了一个**新的** Event 并 set 它，
> 而第 2 轮的回答线程还在等**旧的**那个 Event —— 它永远等不到，于是"日志说停了、声音还在响、
> 历史里还写入了完整回答"。
> 正确做法：`_stop` 属于"当前正在生成的那一轮"，在 `_launch_respond()` 里创建，
> 打断时只 set 不替换。这是**资源生命周期归属**问题，多线程编程的经典坑。

## 三、状态机：四种状态

`src/agent.py:51` 的 `State` 枚举：

```
                    ┌──────────────┐
      启动           │  LISTENING   │◀──────────── 播放结束 / 被打断
      ─────────────▶│   (在听)     │
                    └──────┬───────┘
                           │ VAD 报 start
                           ▼
                    ┌──────────────┐
                    │ USER_SPEAKING│  用户还在说，持续累积音频缓冲
                    └──────┬───────┘
                           │ VAD 报 end（静音 500ms）
                           ▼
                    ┌──────────────┐
                    │   THINKING   │  ASR + LLM 首 token（这段空窗期最难受）
                    └──────┬───────┘
                           │ 第一个音频块到达
                           ▼
                    ┌──────────────┐
                    │ BOT_SPEAKING │  边生成边播
                    └──────┬───────┘
                           │ ① 播完 ② 或被打断
                           └──────▶ 回到 LISTENING
```

**状态机的价值**：每收到一个 VAD 事件，先问"我现在处于哪个状态"，再决定这个事件意味着什么。
同样一个 `start` 事件：
- 在 `LISTENING` → 新的一轮，开始录音
- 在 `BOT_SPEAKING` → **打断**，立刻停播
- 在 `USER_SPEAKING` → 忽略（用户只是停顿了一下又继续）

> **面试点 3：`_on_bot_start` 为什么要判断 `if self.state != State.USER_SPEAKING`？**
> 又是一个真 bug。TTS 的第一块音频到达时播放线程回调 `_on_bot_start`，它会无条件把状态设成
> `BOT_SPEAKING`。但如果此刻用户正在说话（机器人上一句的尾巴还在播，用户已经开口），
> 状态就被抢走了，等用户说完时 `USER_SPEAKING → THINKING` 的转换条件不再成立，
> **那一轮的 `user_speech_end` 永远不触发**——事件日志里那一轮直接没有 ASR 结果。
> 修法一行：只在不是 `USER_SPEAKING` 时才切。

## 四、九个打点事件：一条时间轴

`src/tracer.py` 把每个事件带时间戳写进 `events.jsonl`（每行一个 JSON）。
九个事件名是**固定的**，因为下游 `tools/latency.py` 靠它们算六个指标：

| 事件 | 什么时候打 | 由谁打 |
|---|---|---|
| `user_speech_start` | VAD 判定用户开口 | 主线程 `_begin_utterance` |
| `user_speech_end` | VAD 判定用户说完 | 主线程 `run()` |
| `asr_final` | ASR 出最终文本 | 回答线程 `_respond` |
| `llm_first_token` | LLM 吐出第一个 token | 回答线程 `_respond` |
| `tts_first_audio` | TTS 产出第一块音频 | 回答线程 `_respond` |
| `bot_speech_start` | 第一块音频真的开始播 | 播放线程 → 回调 `_on_bot_start` |
| `bot_speech_end` | 播完了 | 播放线程 → 回调 `_on_bot_end` |
| `barge_in_detected` | 用户打断被确认 | 主线程 `_on_barge_in` |
| `bot_audio_stopped` | 声卡真的停了 | 主线程 `_on_barge_in`（读 `speaker.last_flush_ms`） |

一条典型时间轴（从 `_run8.log` 实测）：

```
t=0.60s   user_speech_start      ← 用户开口
t=2.40s   user_speech_end        ← 静音 500ms 后判定说完
t=2.52s   asr_final              ← ASR 116ms
t=2.53s   llm_first_token        ← LLM TTFT 17ms（mock）
t=2.68s   tts_first_audio        ← TTS 151ms
t=2.68s   bot_speech_start       ← 声卡真的响了
t=4.20s   user_speech_start      ← 用户插话！
t=4.44s   barge_in_detected      ← 确认 240ms
t=4.45s   bot_audio_stopped      ← 14ms 内声卡静音
t=4.45s   bot_speech_end         ← 收尾（被打断也算 end）
```

> **面试点 4：为什么要有 `tts_first_audio` 和 `bot_speech_start` 两个事件？**
> 因为"TTS 生成了音频"和"人真的听到了声音"是两件事，中间隔着播放队列的排队。
> 如果只看 `tts_first_audio`，你会以为延迟 283ms，但实际上音频可能在队列里多等了 100ms。
> **用户感受到的是 `bot_speech_start`**。分开打点才能定位"是模型慢还是队列积压"。

## 五、打断：三步，缺一不可

打断是整个项目最核心的能力，也是 JD 里明确要求的"自然打断"。
`_on_barge_in`（`src/agent.py:339`）做的三件事：

### 第 1 步：让生成侧停下

```python
self._stop.set()      # 回答线程在 LLM 循环和 TTS 循环里检查这个开关
```

回答线程里有两处检查点：LLM 逐 token 循环开头、每句 TTS 之前。
不设这个开关，LLM 会继续生成、TTS 会继续合成——**纯浪费 GPU，还会污染历史**。

### 第 2 步：让播放侧立刻静音，并拿到"已经播到哪儿"

```python
progress = self.speaker.flush()    # 返回 [(seg_id, text, fraction), ...]
```

`flush()`（`src/audio_io.py:126`）做的事：
1. 记下 `was_active`（此刻到底在不在播）
2. `self._gen += 1` —— **代数 +1，播放线程内层循环发现 gen 变了就立刻退出**
3. 清空队列、`self._playing = False`
4. 等播放线程回执（`self._interrupted.wait(timeout=0.3)`），记 `last_flush_ms` ← **这就是 `barge_in_stop` 指标**
5. 返回每个音频段"播了百分之几"

**为什么不用 `terminate()`/`kill()`？** 因为那样会丢掉"播到哪儿"的信息，而这正是第 3 步需要的。
而且 `OutputStream` 被硬杀之后再开会有爆音/设备占用问题。用"代数 + 队列清空 + 20ms 粒度检查"能做到
**约 14ms 停止响应**（实测），比 `terminate` 更干净。

### 第 3 步：把"播出去的部分"写进历史

```python
spoken = played_text(progress)     # src/dialog.py:163
if spoken:
    history.add_assistant(spoken)  # 只写用户真的听到的那部分
```

> **面试点 5：打断后为什么不能把"LLM 完整生成的回答"写进历史？**
> 这是**上下文一致性**问题。假设 LLM 生成"北京今天晴，气温 25 度，适合出门"，
> 用户只听到"北京今天晴"就插话"那明天呢"。
> 如果历史里记的是完整句子，下一轮模型会以为用户已经知道"适合出门"这件事，
> 对话就会"接不上"。用户会立刻感觉到"这机器人没在听我说话"。
>
> 我们用 `played_text()` 按 `fraction`（播放比例）截断：
> `fraction >= 0.999` 算整句；否则按字数比例截，并把末尾的逗号、顿号这类"软符号"去掉
> （不然历史里会出现"北京今天晴，"这种断在中间的话）。
>
> **这是本项目最有技术含量的一处，简历和面试都应该重点讲这个。**

## 六、延迟预算：六个指标怎么分解

`config.yaml` 里的 `eval.budget`：

| 指标 | 定义 | 预算 | 实测 | 含义 |
|---|---|---|---|---|
| `asr_latency` | `user_speech_end` → `asr_final` | 300ms | 116ms | 说完到出文字 |
| `llm_ttft` | `asr_final` → `llm_first_token` | 400ms | 17ms | 首 token 时间（流式的意义所在） |
| `tts_latency` | 首 token → `tts_first_audio` | 300ms | 151ms | 攒够一句到合成出音频 |
| `e2e_first_audio` | `user_speech_end` → `bot_speech_start` | **800ms** | **283ms** | **用户真正感受到的等待** |
| `barge_in_stop` | `barge_in_detected` → `bot_audio_stopped` | 250ms | 14ms | 打断后多久静音 |
| `bot_speech_dur` | `bot_speech_start` → `bot_speech_end` | — | 1463ms | 一句话说多久 |

`e2e_first_audio` 是**唯一真正决定体验**的数字。人耳能接受的对话空窗大约 700~800ms，
超过 1 秒就开始觉得"卡"。

**怎么把它压下来（按收益排序）：**
1. **流式 LLM**（已经在做，省下的就是整个回答的生成时间）—— TTFT 17ms vs 整句 1500ms，差 80 倍
2. **句子级 TTS 切片**（已经在做）—— 不必等 LLM 说完，第一句一到就合成
3. **软断点**（`SentenceSplitter._find_cut` 里 `_SOFT = "，,、：:"`）—— 一句话太长时在逗号处先切，
   提前 200~300ms 出声，代价是语调略微不连贯。< 12 字不切，避免全是碎句。
4. `tts_latency` 里有一部分是**攒句等待**，不是模型慢。加软断点后从 346ms 降到 151ms。

> **面试点 6：你的 283ms 是不是假的？因为 LLM 是 mock。**
> 诚实回答：`asr_latency`、`tts_latency`、`barge_in_stop` 是真的（SilentTTS 按字数模拟真实
> 合成速度，ASR 是 MockASR 加固定 60ms），但 `llm_ttft` 是 mock 的。
> 换真模型后 `llm_ttft` 大约 200~400ms（取决于网络/GPU），`e2e_first_audio` 会变成 500~700ms，
> 仍然在预算内。
> **主动说明哪部分是真数据、哪部分是模拟，比被追问出来的效果好得多。**

## 七、为什么是 20ms 一块

`audio.block_ms = 20`，16000Hz × 20ms = **320 个采样点**一块。

太小（比如 5ms）：回调太频繁，CPU 在调度上浪费，Python 层开销大。
太大（比如 100ms）：打断响应变慢——最坏情况要等 100ms 才发现该停，
用户已经听到一段"多出来的话"。

**20ms 是权衡点**：延迟可控（最坏 20ms + 写声卡的缓冲），开销可接受。
这也是 WebRTC 默认的音频帧长。

> 顺带一个细节：`_pump()` 里把每个 TTS 音频块**再拆成 20ms 小片**写声卡，
> 每片写之前检查一次 `gen`。这样不管 TTS 吐出来的块多大，打断响应粒度都是 20ms。

## 八、回声门控（echo gate）：机器人说话时怎么还能听见人

这是级联架构的一个硬问题：**机器人自己的声音会被麦克风收回去**，
如果不处理，VAD 会认为"用户一直在说话"，机器人会自己打断自己。

`src/audio_io.py` 的 `BaseSpeaker` 有 `on_start` / `on_end` 回调，
`src/agent.py` 的 `_on_bot_start` 里调 `vad.set_echo_mode(True)`，`_on_bot_end` 里关掉。

打开时（`src/vad.py:163` 附近）：
- 能量阈值 ×`echo_gate.threshold_ratio`（2.5 倍）—— 只有比"回声"响得多的声音才算人声
- 需要连续说话的帧数 ×`echo_gate.min_speech_ratio`（2.0 倍）—— 环境噪音不容易误触发

**这就是"播放期抬阈值"的简单版 AEC**。真正的声学回声消除（AEC）需要参考信号做自适应滤波
（WebRTC 的 AEC3），我们没做，因为在耳机/近讲麦克风场景下抬阈值就够了。

> **面试点 7：为什么不用 WebRTC 的 AEC？**
> AEC3 是 C++ 实现 + 需要精确的时钟对齐和参考信号通道，Python 侧通常通过 `webrtc-audio-processing`
> 绑定或 `pyaudio` 的完整双工流来做。在当前这台机器上装不上（PyPI 不可达），
> 而且对"戴耳机的桌面场景"收益不明显。
> **我用阈值门控做了第一层保护，并在 README 里说明这是简化版**——
> 生产环境要换成 AEC3 + 双讲检测（double-talk detection）。
