## 2. `src/config.py` — 配置（`load_config` 在 208 行）

结构：每个 yaml 段落对应一个 `@dataclass`。
`_get(d, key, default)`（46 行）是安全取值的小工具，避免 `KeyError`。

**三个细节值得注意：**

1. **`_warn_unknown`（54 行）**：如果你在 yaml 里把 `energy_threshold` 拼成 `energy_thresold`，
   程序不会崩，而是打印"未知配置项，可能是拼错了"。因为用 dataclass 逐字段构造，
   拼错的键会被**静默忽略**——这是最坑的一种 bug（改了配置没生效）。
2. **`AudioCfg.block_samples`（84 行）**：把 `block_ms` 换算成采样点数。
   `16000 * 20 / 1000 = 320`。整个程序里所有"块"的大小都由它决定。
3. **`_validate_cfg`（317 行）**：启动时校验不合理的组合，例如
   `mode=sim` 却给了 `mic_device`、`block_ms=5`（太小）、`silence_ms=50`（说完判太快）。
   **早失败**比"跑到一半行为诡异"好得多。

`OpenAICompatCfg.api_key`（140 行）是 `@property`：从环境变量读，不写进 yaml。
因为 yaml 经常被提交到 git。

## 3. `src/miniyaml.py` — 为什么手写一个 YAML 解析器

**背景**：这台机器 `pip` 访问不了 PyPI（试 `Invoke-WebRequest https://pypi.org/simple/pyyaml/`
直接报"基础连接已经关闭"），`pyyaml` 装不上。如果配置文件非要 pyyaml 才能读，项目就跑不起来。

所以写了一个**只支持本项目用到的 YAML 子集**的解析器（约 200 行）：

| 支持 | 不支持 |
|---|---|
| 嵌套映射、块列表 `- item` | 锚点 `&`/`&*`、多文档 `---` |
| 行内列表 `[0, 10, 5]` | 复杂 flow mapping `{a: 1, b: 2}` 嵌套 |
| 块标量 `|` 和 `>`（多行文本） | 性别/时间类型转换 |
| 注释 `#`、`null`/`true`/`false`、数字、引号字符串 | |

`config.py` 里的切换逻辑：

```python
try:
    import yaml as _pyyaml
    YAML_SOURCE = "PyYAML"
    def _load_yaml_file(path): ...
except ImportError:
    from . import miniyaml as _miniyaml
    YAML_SOURCE = "miniyaml（内置，零依赖）"
```

> **面试点**：这是"能不能装上"和"代码优雅"的取舍。
> 面试官听了会知道你不是只会 `pip install` 的人——你会为交付环境做兜底。
> 但也要说清楚：**这不是通用 YAML 解析器**，如果配置变复杂就该回到 pyyaml。

## 4. `src/tracer.py` — 埋点（`Tracer` 34 行，`log` 46 行）

```python
def log(self, turn, event, t=None, **extra):
    with self._lock:
        self._fh.write(json.dumps({...}, ensure_ascii=False) + "\n")
        self._fh.flush()
```

**三个设计点：**

1. **每行一个 JSON（JSONL）**：可以边写边读，进程崩了也不丢已写的数据。
   如果用一个大 JSON 数组，崩了就全废。
2. **`flush()` 每条都刷**：性能开销可忽略（每秒几行），换来"断电也不丢"。
3. **`with self._lock`**：三个线程都会打点，必须加锁，否则会写坏行。
4. **`now()`（82 行）= `time.perf_counter()`**：不是 `time.time()`。
   `perf_counter` 单调递增、精度高，专门用来测间隔。用 `time.time()` 会被系统对时影响
   （实测出现过算出负延迟的情况）。

`summarize()`（92 行）是个轻量兜底：如果没有 `tools/latency.py`，退出时也能给个中位数汇总。

## 5. `src/vad.py` — 语音活动检测

### `BaseVAD`（50 行）：状态机骨架

```python
self._need_speech_frames = int(round(min_speech_ms / block_ms))  # 160/20 = 8 帧
self._need_silence_frames = int(round(silence_ms / block_ms))    # 500/20 = 25 帧
```

`process(block, at)`（82 行）返回 `VadEvent(kind, at)`，`kind` 只有三种：
`None`（没变化）、`"start"`（开始说话）、`"end"`（说完了）。

**为什么要"连续 N 帧"才算**：单帧误判太容易（键盘声、关门声）。
连续 8 帧（160ms）有人声才算"开口"，连续 25 帧（500ms）静音才算"说完"。
这两个数字直接决定体验：`min_speech_ms` 太小会被噪音触发，`silence_ms` 太大显得反应慢。

### `EnergyVAD.is_speech`（163 行）：★ 这里有个必讲的 bug

当前逻辑（**修好后的版本**）：

```python
r = self.rms(block)
thr = max(self._noise_floor * self.adapt_ratio, self.base_threshold * 0.5)
if self._echo_mode:
    thr *= self.echo_threshold_ratio
is_sp = r > thr
if self.adaptive and r < self._noise_floor * 2.0:   # ← 关键判断
    self._noise_floor = (1-alpha)*self._noise_floor + alpha*r
self._noise_floor = max(self._noise_floor, 1e-4)
self._noise_floor = min(self._noise_floor, self.base_threshold * 3.0)
return is_sp
```

**修之前是** `if self.adaptive and not self._in_speech:` —— 只要"还没确认在说话"就用当前帧更新噪声底。

**为什么这是灾难**：打断场景下，用户插话的第 1 帧还没被确认为语音（要连续 8 帧），
于是这一段**人声被当成背景噪音**喂进了噪声底 EMA。噪声底从 1e-4 一路爬到 0.13，
阈值 = 3 倍 = 0.39 —— 之后**再大声的人声也超不过阈值**，VAD 永久失灵。
表现就是：机器人播报期用户插话，100% 漏检，一次都打断不了。

**修法**：只在"这一帧真的像背景"时才更新（`r < noise_floor * 2.0`），
并给噪声底加上下夹紧，防止它跑飞。

> **这是本项目最值得讲的一个 bug**：它不在"打断逻辑"里，而在"打断逻辑依赖的 VAD"里。
> 表层现象是"打断不工作"，根因在噪声底自适应。面试时这么讲，比讲十个 CRUD 都加分。

### `SileroVAD`（190 行）：神经网络版

`silero_vad` 是 PyTorch 的轻量 VAD（约 2MB），比能量阈值可靠得多，尤其是嘈杂环境。
懒加载（第一次 `is_speech` 才 import），因为它要 torch，而 mock 模式不想装 torch。
`echo` 模式下阈值 ×1.3（比能量版的 2.5 保守，因为神经 VAD 本来就抗噪）。

## 6. `src/audio_io.py` — 麦克风 + 可打断播放（★ 核心之一）

### `AudioChunk`（37 行）/ `SegProgress`（55 行）

```python
@dataclass
class AudioChunk:
    pcm: np.ndarray
    seg_id: int        # 第几段（一句话一段）
    text: str          # 这段对应的文字（打断截断历史要用）
    index: int         # 段内第几块
    is_last: bool      # 这一段/这一轮是否结束
```

**`text` 字段是关键**：音频块必须带着"它对应的文字"，否则打断时没法算"用户听到哪几个字"。

`SegProgress.fraction`（63 行）= `played_samples / total_samples`。这就是截断比例。

### `BaseSpeaker.flush()`（126 行）：★ 打断的第二只脚

```python
def flush(self):
    was_active = self._playing or not self._q.empty()
    t0 = perf_counter()
    with self._q.mutex:
        self._q.queue.clear()      # 清空待播
    self._gen += 1                 # ← 代数 +1，播放线程看到就退出
    self._playing = False
    progs = [...]                  # 每段播了百分之几
    self._segs = {}
    if was_active:
        self._interrupted.wait(timeout=0.3)   # 等播放线程回执
        self.last_flush_ms = (perf_counter() - t0) * 1000
        self.on_end()               # 主动通知"这一轮结束了"
    return progs
```

四个要点：

1. **`_gen`（代数）机制**：不用锁去 `join` 播放线程，而是让播放线程在每写一小片前检查
   `if gen != self._gen: return False`。这是**协作式取消**，比强杀干净，粒度 20ms。
2. **`self._interrupted` 回执**：`flush()` 必须知道"播放线程真的停了"才能返回，
   否则 `bot_audio_stopped` 时间戳会和实际差一个调度周期（我们最初就是恒 0ms，因为根本没等）。
3. **`on_end()` 要主动调**：如果只清空队列不通知，状态机会永远卡在 `BOT_SPEAKING`，
   echo 门控也不会关 → 机器人聋了。
4. **`_segs` 清空时机**：最初 `flush()` 后没清，导致同一段被统计两次。

### `_pump()`（187 行）：播放循环

```python
while True:
    chunk = self._q.get()
    gen = self._gen
    for piece in 拆成 20ms 小片:
        if gen != self._gen:            # 被打断了
            self._interrupted.set()
            return
        ok = self._write(piece, gen)
        if not ok:                       # 写失败（设备没了/打断）
            self._interrupted.set()      # ← 必须有，否则 flush 白等 300ms
            return
        if ok and seg is not None:
            seg.played_samples += len(piece)   # 真写进去了才算听到
```

**两个易错点**：
- `_write` 返回 False 时也必须 `set()` 回执（我们踩过：只 break，flush 等满超时）
- `played_samples` 只能在**写成功之后**加，否则会多算已经听到的字数

### 三个 Speaker 实现

| 类 | 用途 | 关键 |
|---|---|---|
| `BaseSpeaker`（69） | 抽象基类，管队列/代数/进度 | 所有逻辑都在这里 |
| `SoundDeviceSpeaker`（235） | 真声卡，`sd.OutputStream.write()` 阻塞写 | 单测/CI 跑不了 |
| `SimSpeaker`（282） | 假扬声器，**按真实时间 sleep** | 关键：不是"立刻返回"，否则延迟数据全假 |

> `SimSpeaker` 为什么要 sleep：如果它瞬间就"播完"了，`bot_speech_dur` 会是 0ms，
> `barge_in_stop` 也测不出来，整条时间轴全是 0。**模拟真实时间流速**才能拿到可信的指标。

### Mic 三个实现

| 类 | 用途 |
|---|---|
| `BaseMic`（315） | 统一 `_apply_gain` 增益 |
| `SoundDeviceMic`（338） | 真麦克风，`InputStream` 回调把音频塞进队列 |
| `ScriptedMic`（393） | ★ 脚本音源，按 `DEFAULT_SCHEDULE` 造音频 |

`ScriptedMic.DEFAULT_SCHEDULE`：

```python
[(0.6, 2.4), (4.2, 5.6), (10.5, 11.9), (15.0, 16.4), (20.0, 21.2)]
```

**第二段（4.2s）是故意设计的**：它落在机器人第一轮回答（2.7s~4.5s）的中间，
所以一定会触发打断。**没有麦克风也能测打断**——这是 sim 模式存在的意义。

有声部分是 `220Hz 正弦 × 0.25 × (1 + 0.15·sin(2π·3t))`（加 3Hz 抖动让它不像纯音），
静音部分是 `randn * 3`（真的有底噪，不是全零，否则自适应噪声底学不到东西）。

## 7. `src/asr.py` — 语音识别（三个后端）

接口就一个方法：`transcribe(pcm, sample_rate=16000) -> str`。

| 类 | 说明 |
|---|---|
| `MockASR`（43） | 按顺序返回六句预设中文，`sleep(60ms + 音频时长*3%)` 模拟真实耗时 |
| `FunASRBackend`（79） | ★ 真的。`AutoModel(model="paraformer-zh", vad_model="fsmn-vad", punc_model="ct-punc")` |
| `FasterWhisperASR`（133） | 备选，`WhisperModel("small")` |

`FunASRBackend.transcribe`（117 行）三个细节：

1. **`int16 → float32`**：FunASR 要 float32（[-1,1]）。`max(pcm) > 1.5` 就判定是 int16 并 `/32768`。
2. **`batch_size_s=60`**：FunASR 按秒分批，60 秒足够。
3. **太短的音频直接返回空**：`< 0.1s` 不送模型（省一次推理，也避免模型输出乱码）。

`build_asr(cfg)`（171 行）**失败自动降级**：装不上 FunASR 就退回 MockASR 并打印原因。
这样"少装一个包"不会让整个 demo 跑不起来。

> **面试点**：`asr.mode = utterance` 意思是"攒够一整句再送模型"（非流式）。
> 这正是 `asr_latency` 那 116ms 的来源。真要流式，FunASR 有 streaming 模式，
> 但要用 `chunk_size=[0,10,5]` 那套参数（config 里已经预置了，但没实现，
> 因为流式 ASR 的 partial result 处理会让整个 demo 复杂度翻倍）。
> **承认"我知道怎么做但这次没做，因为收益/复杂度不划算"，是成熟的判断。**

## 8. `src/llm.py` — 大模型（三个后端）

接口：`stream(messages) -> Iterator[str]`，逐 token yield。

| 类 | 说明 |
|---|---|
| `MockLLM`（52） | 六条 20~45 字中文回复，按 2 字一组吐，`token_delay_ms=16` |
| `OpenAICompatLLM`（92） | ★ 推荐。任何 OpenAI 兼容端点（DeepSeek、vLLM、ollama、OneAPI） |
| `LocalHFLLM`（140） | 本地 transformers + 4bit，需要显存 |

`OpenAICompatLLM.stream`（116 行）：

```python
resp = self._client.chat.completions.create(
    model=self.model, messages=messages, stream=True,
    temperature=self.temperature, max_tokens=self.max_tokens,
)
for chunk in resp:
    delta = chunk.choices[0].delta.content
    if delta: yield delta
```

**为什么默认走 API 而不是本地 7B**：8GB 显存要同时装 FunASR(1.5G) + CosyVoice2(1.6G) + 7B-4bit(5.0G)
= 8.1G，**已经爆了**。API 方案零显存、当天能跑通。本地 7B 作为可选（`hf_local`）。

`LocalHFLLM.stream`（172 行）用 `TextIteratorStreamer` + `threading.Thread`：
`model.generate()` 是阻塞的，必须放到另一个线程里跑，主线程才能从 streamer 里逐块取。

> **`MockLLM.token_delay_ms = 16`** 这个值是有讲究的：16ms/2字 ≈ 125 字/秒，
> 接近真实在线模型的输出速度。原来是 28ms，导致 `llm_ttft` 看起来「有 17ms 已经很好了」
> 但整体偏慢——**假模型慢不该算进管线延迟**，会让指标失真。

## 10. `src/dialog.py` — 历史 + 切句 + 截断（★ 核心之三）

### `History`（32 行）

```python
self._msgs = []          # [{"role": "user"/"assistant", "content": ...}]
self.max_turns = 6       # 最多 6 轮
self.max_chars = 1200    # 总字数上限
```

`_trim()`（85 行）两道保险：
1. 按轮数截断（`max_turns`）
2. 按总字数从**最老的**开始丢，但保证最后两条不丢，且历史以 `user` 开头

**为什么两个都要**：轮数控制"话题漂移"，字数控制"token 成本"。
只按轮数，遇到长回答会爆上下文；只按字数，会丢掉最近几轮的结构。

`drop_last_assistant()`（62 行）：打断时如果这一轮的回答还没进历史，先删掉再写"播出去的部分"。

### `SentenceSplitter`（103 行）

`push(token)` 边收 token 边切句，返回 `List[str]`。

```python
_HARD = "。！？；!?;\n"     # 硬断点：一定切
_SOFT = "，,、：:"          # 软断点：太长了才切
```

`_find_cut`（149 行）的优先级：
1. 遇到硬断点 → 切
2. 超过 `max_len=60` 字 → 在最近的软断点切
3. 软断点且已攒够 `soft_min_len=12` 字 → 切（**提前出声，牺牲语调连贯换延迟**）

**为什么要切句**：LLM 是流式的，如果等整段说完再送 TTS，首字延迟就等于"整个生成时间"。
切句让 TTS 和 LLM **并行**工作。

**为什么软断点要 ≥12 字**：太短的句子拼起来说的是"断断续续的机器人"
（"今天" / "天气" / "不错"），听起来非常假。

### `played_text`（163 行）：★ 打断截断的核心

```python
def played_text(progress):
    out = []
    for seg_id, text, frac in progress:
        if frac >= 0.999:
            out.append(text)                      # 整句都播完了
        elif frac > 0:
            n = max(1, int(round(len(text) * frac)))
            out.append(text[:n].rstrip("，,、：: "))  # 按比例截，去掉末尾软符号
    return "".join(out)
```

**为什么末尾要去掉逗号顿号**：`"北京今天晴，"` 这种断在中间的历史，
会让下一轮模型误判"这句话没说完"，生成奇怪的回答。

**这是整个项目最"产品化"的一处**：大多数 demo 打断后直接把完整回答写进历史，
对话就会出现"机器人以为你已经知道它没说完的话"的诡异感。

## 11. `src/agent.py` — 核心（★ 先读这个）

### `run()`（108 行）：主循环

```python
while True:
    for block in self.mic.blocks():
        ev = self.vad.process(block, tracer.now())
        if ev.kind == "start":
            self._begin_utterance(block, barge_candidate=(state == BOT_SPEAKING))
        elif ev.kind == "end":
            if state == USER_SPEAKING: → 启动回答线程
        # 打断确认：VAD start 之后还要再等 (min_speech_ms - vad.min_speech_ms)
```

**重点**：主循环**从不阻塞在 ASR/LLM 上**。它只做一件事——读麦克风、喂 VAD、发事件。
所有耗时工作都在回答线程里。这是"能打断"的结构前提。

### 打断确认的额外等待（`_barge_at` + `extra_ms`）

```python
extra_ms = max(0, self.cfg.barge_in.min_speech_ms - self.cfg.vad.min_speech_ms)
# barge_in.min_speech_ms=240, vad.min_speech_ms=160 → 还要再等 80ms
```

**为什么要二次确认**：`vad.min_speech_ms=160ms` 已经要求连续 8 帧有人声了，
但打断的代价很大（打断正在说的话），误触发的体验极差。
所以打断单独配一个更长的阈值 240ms。这两个参数**故意分开**：
VAD 的灵敏度是为"开始录音"调的，打断的灵敏度是为"打断"调的。

### `_respond()`（238 行）：回答线程

```
ASR → asr_final
    → history.add_user
    → LLM.stream() 逐 token
        → 首个 token 打 llm_first_token
        → 喂给 SentenceSplitter
        → 每得到一句：tts.synth() → speaker.enqueue(带 seg_id/text)
             → 第一块音频打 tts_first_audio
    → 末尾塞一个 is_last=True 的空块（通知播放端"这一轮完了"）
    → _wait_speaker() 等播完
    → history.add_assistant(完整回答)   ← 注意：没被打断才走这里
```

**`is_last` 空块**这个设计值得说：播放线程怎么知道"这一轮播完了"？
靠一个 `pcm` 长度为 0、`is_last=True` 的哨兵块。比"设个 flag + 轮询"更干净。

### `_on_barge_in()`（339 行）：★ 三步走

```python
self._stop.set()                      # 1. 让生成侧停
progress = self.speaker.flush()       # 2. 停播 + 拿到播到哪儿
tracer.log(turn, "barge_in_detected")
spoken = played_text(progress)
if spoken: self.history.add_assistant(spoken)   # 3. 只写听到的部分
tracer.log(turn, "bot_audio_stopped", extra={"ms": self.speaker.last_flush_ms})
```

顺序不能变：先停生成，再停播放（否则生成侧会继续往队列里塞），最后写历史。

### 状态保护（`_on_bot_start` 376 行 / `_on_bot_end` 387 行）

```python
def _on_bot_start(self):
    if self.state != State.USER_SPEAKING:      # ← 这行是 bug 修出来的
        self.state = State.BOT_SPEAKING
    self.vad.set_echo_mode(True)               # 打开回声门控
```

**为什么**：第一块音频到达时，用户可能已经在说话了（上一句的尾巴）。如果无条件切成
`BOT_SPEAKING`，那一轮的 `user_speech_end` 就永远不触发了。

### `_wait_speaker()`（394 行）

轮询 `speaker.is_playing`，每 20ms 查一次，带超时。
轮询不如事件通知优雅，但简单可靠，而且 20ms 精度对这里的用途足够。

## 12. `src/main.py` — 组装（`main` 47 行）

`main()` 干四件事：

1. 解析参数（`--mode`、`--backend`、`--max-turns`、`--list-devices`）
2. 按 `mode` 造 mic/speaker：`sim` → ScriptedMic + SimSpeaker；`mic` → 真设备
3. 打印启动横幅（当前后端的每个组件名字，方便截图/复现）
4. 退出时 `tracer.close()` 然后调 `tools/latency.py` 出报告

**这里没有业务逻辑**，只有"装配"。这样任何组件都能单独替换（换 TTS 不改 agent）。

## 13. `tools/latency.py` — 从事件算指标

读 `events.jsonl`，按 turn 分组，配对 start/end 事件算 delta，输出 markdown 表或 `--json`。

**它是独立脚本**：不用跑 demo 也能用，`python tools/latency.py --json` 直接读现成的日志。
这样你在面试前可以攒多份日志做对比（比如"改软断点前 vs 后"）。

## 14. `setup/` 四个脚本

| 文件 | 干什么 | 什么时候跑 |

| `install_windows.ps1` | 建 venv、装 torch/依赖、跑体检 | 到新机器第一件事 |


面试时这个文件可以直接演示"工程完成度"。
